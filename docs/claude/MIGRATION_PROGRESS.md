## Step 4: Link Neon Auth identity to public.users — done (trial only)
- What I did: wrote `neon/migrations/0001_users_neon_auth.sql` (Neon only, idempotent) and applied it to the Neon trial twice. It (1) repoints `public.users.id` from `auth.users` to `neon_auth."user"(id)` ON DELETE CASCADE; (2) adds trigger `on_neon_auth_user_created` on `neon_auth."user"` that creates the profile row (student, no tenant), replacing `on_auth_user_created`; (3) drops `on_user_claims_change` (roles are read from `public.users`, not the token); (4) makes `current_user_role`, `current_tenant_id`, `current_student_group_ids` return nothing for a deactivated account (`is_active IS NOT FALSE`).
- Why (4): on Supabase the proxy blocked deactivated users with the token's `is_active` claim. A Neon Auth token has no such claim; the first e2e run showed a deactivated teacher still reading their groups. Now the database denies it on the next query (instant, no token wait).
- Checks run and their result (scratchpad `neon/e2e4.mjs`, real Neon Auth sign-ups + Data API): sign-up 200/200; profile rows created by trigger 2/2; teacher A sees only `A-group`, teacher B only `B-group`; no token → 400, forged token → 400; deactivated teacher → `[]`; cleanup left 0 auth users / 0 users / 0 tenants / 0 groups. Timing (`measure3.mjs`, 5,000 Neon Auth users): 0.442 ms without RLS vs 0.606 ms with RLS (median), unchanged by the `is_active` check. Second apply of the migration: no error, same end state.
- Open issues: (a) the live Supabase schema is untouched; this file must not be run there. (b) Code still reads role/is_active from Supabase token metadata (`src/proxy.ts`, `getAuthUser`, login page); step 6 moves that. - Measured (probe Worker in scratchpad `neon/hd-probe`, run with `wrangler dev --remote` = real Cloudflare edge + real Hyperdrive, not a public deploy; edge location `ZDM`; 3 runs × 10 samples):
  - With caching on, `select 1` took 1 ms: Hyperdrive answered from its cache without asking the database. Cached reads can show a stale exam state or grade for up to a minute, so caching stays off.
  - With caching off: one round trip to Neon (Frankfurt) ≈ **60–63 ms**. An RLS read written as a normal transaction (begin, set claims, set role, select, commit = 5 round trips) ≈ **300–317 ms**. The same work sent as **one** message ≈ **60–63 ms**.
  - Conclusion for step 9: every request must reach the database in one message (claims + role + query together), or it pays ~60 ms per extra statement.
- Checks run and their result: `npm run cf:preview` starts with the binding ("Hyperdrive will connect to this database during local development"); `GET /` 200, `GET /login` 200.
- Limits (Cloudflare pricing page, read 2026-10-22): Hyperdrive is on the Free plan with **100,000 queries/day**; Paid is unlimited. Production will need the Paid Workers plan.
