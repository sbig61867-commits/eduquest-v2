# المرحلة 9 — الدفع والتسعير: التشخيص الكامل وخطة البناء

## 0) اكتشاف يُصحِّح تقييم المرحلة 4: **صفحة `/pricing` معطَّلة فعلياً الآن، لا مجرد "غير مُرسَلة لـ git"**

راجعت [src/lib/pricing/plans.ts](src/lib/pricing/plans.ts) مباشرة، والسطر الأول الفعلي في الملف:
```ts
export const pricingEnabled = false
```
مع تعليق صريح فوقه: *"قسم الأسعار مخفي حالياً: الروابط في الهيدر/الفوتر لا تظهر و /pricing تُرجع 404."* **هذا يعني أن أي زائر حقيقي الآن لا يرى صفحة تسعير إطلاقاً** — كل ما راجعته في المرحلة 4 (بنية الخطط، الأسئلة الشائعة، CTA) موجود في الكود لكنه **غير منشور للجمهور بعد**. هذا يغيّر تماماً إلحاح المشكلة: ليست "صفحة تسعير ضعيفة"، بل **غياب كامل ومتعمَّد لأي صفحة تسعير حالياً.**

## 1) التشخيص الكامل — ماذا يوجد فعلاً وماذا لا يوجد

| العنصر | الحالة |
|---|---|
| بنية خطط مُصمَّمة (3 مستويات) | ✅ موجودة في الكود، معطَّلة عن النشر |
| صفحة `/pricing` منشورة للجمهور | ❌ `pricingEnabled = false` |
| بوابة دفع (Stripe/أي بديل) | ❌ صفر — لا تبعية واحدة في `package.json` |
| جداول `subscriptions`/`invoices`/`usage` | ❌ غير موجودة في `schema.sql` إطلاقاً |
| آلية Webhooks لأي مزوّد دفع | ❌ غير موجودة |
| تسجيل ذاتي (self-serve signup) بعد الدفع | ❌ غير موجود — كل حساب يُنشأ عبر دعوة من الإدارة يدوياً |
| آلية الدفع الفعلية الحالية | **فاتورة يدوية بالاتفاق المباشر** — مذكور حرفياً في الأسئلة الشائعة: *"بالاتفاق المباشر مع إدارة المنصة عبر فاتورة شهرية أو سنوية"* |
| صفحة سياسة الاسترجاع (Refund Policy) | ❌ غير موجودة |
| اتفاقية معالجة البيانات (DPA) | ❌ غير موجودة |
| بند "القانون الحاكم" (Governing Law) في الشروط | ❌ غير موجود — راجعت `policy.tsx` بالكامل، لا ذكر لأي دولة/اختصاص قضائي |

**الخلاصة:** النموذج الحالي هو **"مبيعات مؤسسية يدوية بالكامل"** (enterprise sales-led)، وهو **نموذج شرعي وشائع فعلاً لعملاء B2B كبار** (الخطة "جامعة كاملة" `priceMonthly: null` مصمَّمة لهذا أصلاً) — **لكنه غير كافٍ وحده** لأنه لا يتيح حتى المسار الأبسط: مؤسسة صغيرة تريد الدفع فوراً ببطاقة ائتمان بلا مفاوضة.

## 2) تصميم نظام الفوترة الموصى به

### أ) نموذج الخطط: **هجين — هو بالضبط ما صُمِّم بالفعل، أبقِ عليه**
`plans.ts` يستخدم نموذجاً هجيناً ذكياً: سعر ثابت بحد أقصى طلاب (Institution: $149 حتى 500 طالب) بدل سعر لكل طالب بشكل صارم — هذا **أفضل تجارياً** من "لكل مقعد" الصرف لأن الجامعات تكره عدم القدرة على التنبؤ بالفاتورة الشهرية. **لا تغيّر هذا الجزء.**

### ب) فترة تجريبية وحدود الاستخدام
- خطة `pilot` (30 يوماً، حتى 50 طالباً، بلا بطاقة ائتمان) **موجودة ومصمَّمة جيداً بالفعل.**
- **الناقص:** لا آلية تقنية فعلية لإنفاذ الحدود (50 طالباً، 500 طالباً) — لا عمود `plan_id`/`student_limit` على جدول `tenants`، ولا فحص في `api/admin/create-user` يمنع تجاوز الحد. **حالياً أي مستأجر تجريبي يمكنه فعلياً إضافة عدد غير محدود من الطلاب بلا أي قيد برمجي** — الحد "50 طالباً" وعد تسويقي فقط، غير مُنفَّذ تقنياً.

### ج) مخطط قاعدة بيانات مقترح (جاهز للتطبيق، يتبع اتفاقيات المشروع الموثَّقة)

```sql
-- ملف مقترح: supabase/billing_migration.sql (لم يُطبَّق — تصميم فقط)

CREATE TABLE subscriptions (
  id                UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  tenant_id         UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  plan_id           TEXT NOT NULL,              -- 'pilot' | 'institution' | 'university'
  status            TEXT NOT NULL DEFAULT 'trialing',
                    -- trialing | active | past_due | canceled
  student_limit     INTEGER,                    -- NULL = بلا حد (خطة الجامعة الكاملة)
  billing_period    TEXT NOT NULL DEFAULT 'monthly',
  current_period_end TIMESTAMPTZ,
  provider          TEXT,                       -- 'stripe' | 'manual' | ...
  provider_sub_id   TEXT,                        -- معرّف الاشتراك عند المزوّد الخارجي، NULL للفوترة اليدوية
  created_at        TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(tenant_id)                              -- مستأجر واحد = اشتراك واحد نشط
);

CREATE TABLE invoices (
  id            UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  tenant_id     UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  subscription_id UUID REFERENCES subscriptions(id) ON DELETE SET NULL,
  amount_cents  INTEGER NOT NULL,
  currency      TEXT NOT NULL DEFAULT 'USD',
  status        TEXT NOT NULL DEFAULT 'pending', -- pending | paid | failed | manual
  provider_invoice_id TEXT,
  issued_at     TIMESTAMPTZ DEFAULT NOW(),
  paid_at       TIMESTAMPTZ
);

-- عداد استخدام يومي (لتقارير الفوترة ولإنفاذ حدود الخطة فعلياً)
CREATE TABLE tenant_usage_daily (
  tenant_id     UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  day           DATE NOT NULL,
  active_students INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (tenant_id, day)
);
```
كل هذا **جداول قراءة فقط للتطبيق العادي** — الكتابة تتم حصراً عبر service-role client (نفس نمط المشروع الحالي)، ولا سياسات RLS معقدة مطلوبة لأن الفوترة إدارية بطبيعتها (`SELECT` فقط لصاحب المستأجر + super_admin).

### د) إنفاذ الحدود فعلياً (الجزء المفقود تقنياً)
إضافة فحص بسيط في `api/admin/create-user` (المسار الوحيد لإنشاء حساب طالب): قبل الإدراج، `SELECT count(*) FROM users WHERE tenant_id=... AND role='student' AND is_active=true`، ومقارنته بـ `subscriptions.student_limit` — رفض بـ 402/403 مع رسالة واضحة "بلغتم حد خطتكم، رقّوا الاشتراك" بدل صمت السماح غير المحدود الحالي.

## 3) بوابات الدفع — مقارنة عملية

| البوابة | الملاءمة | القيد الأهم |
|---|---|---|
| **Stripe** | الأنسب عالمياً لو الكيان القانوني مسجَّل في بلد مدعوم (أمريكا/أوروبا/أغلب الخليج عبر Stripe Atlas أو تسجيل مباشر) | يتطلب كياناً تجارياً مسجَّلاً بشكل رسمي — لا يعمل بحساب شخصي |
| **Paddle / Lemon Squeezy** (Merchant of Record) | **الأسهل للبدء بلا كيان تجاري معقّد** — يتصرفان كـ"تاجر مسجَّل" نيابة عنك، يتوليان الضرائب/الامتثال | عمولة أعلى قليلاً من Stripe المباشر، لكن التعقيد القانوني أقل بكثير — **موصى به كنقطة انطلاق** |
| **Moyasar / Tap / HyperPay / PayTabs** (خليجية/إقليمية) | دعم مدى وApple Pay المحليين، تسوية بالريال/الدرهم مباشرة — **يبني ثقة أعلى مع جامعات محلية** | كل منها يتطلب تسجيلاً تجارياً محلياً في بلد التشغيل |
| **فاتورة يدوية بتحويل بنكي** | **الأنسب للخطة "جامعة كاملة"** — مؤسسة كبيرة تفضّل فاتورة رسمية بأي حال | لا يصلح كمسار وحيد — يستبعد أي عميل صغير يريد الدفع فوراً |

**التوصية العملية:** **Paddle أو Lemon Squeezy للخطتين "تجريبية" و"مؤسسي"** (تفعيل فوري ببطاقة، بلا تعقيد قانوني إضافي على المالك الفردي)، **+ الإبقاء على الفاتورة اليدوية لخطة "جامعة كاملة"** (النمط الصحيح أصلاً للعملاء الكبار). لا حاجة لبوابة خليجية محلية إلا إذا أثبتت التجربة أن جامعات محلية ترفض الدفع الدولي فعلياً — لا تُبنَ مسبقاً بلا دليل طلب حقيقي.

## 4) Webhooks — النمط المتوافق مع بنية المشروع الحالية
راوٍ جديد `POST /api/webhooks/[provider]` (خارج نطاق `proxy.ts` — يجب إضافته لـ`PUBLIC_PREFIXES` مثل بقية نقاط الدخول العامة الموثَّقة سابقاً) يتحقق من توقيع الطلب (HMAC الخاص بالمزوّد)، ثم يكتب عبر service-role client إلى `subscriptions`/`invoices` — **نفس نمط "تفويض بالجلسة ثم كتابة بالعميل المميز" المُستخدَم في كل مسارات API الأخرى**، مع فارق أن التفويض هنا توقيع تشفيري لا جلسة مستخدم.

## 5) الصفحات القانونية الناقصة
1. **سياسة الاسترجاع (Refund Policy)** — بند بسيط كافٍ في هذه المرحلة (مثال: "استرجاع كامل خلال 14 يوماً من أول دفعة مؤسسية، لا استرجاع على الأشهر المستخدَمة بعدها").
2. **اتفاقية معالجة البيانات (DPA)** — مطلوبة تعاقدياً من أي جامعة جادة قبل التوقيع (تُلزم المنصة بمعالجة بيانات الطلاب وفق تعليمات الجامعة فقط). يمكن البدء بقالب DPA قياسي (متاحة قوالب مجانية موثوقة) مع تخصيص بسيط.
3. **بند "القانون الحاكم"** يُضاف لصفحة `/terms` الموجودة أصلاً — سطر واحد يحدد دولة/اختصاص التقاضي، ضروري قانونياً وغائب حالياً.

## 6) خارطة تنفيذ مرحلية
| المرحلة | الإجراء |
|---|---|
| **فورية (بلا بوابة دفع بعد)** | تفعيل `pricingEnabled = true` — الصفحة جاهزة فعلياً وتستحق النشر الآن، حتى بفاتورة يدوية فقط |
| **قبل أول دفعة حقيقية** | إضافة جداول `subscriptions`/`invoices`، وفحص حد الطلاب الفعلي في `create-user` |
| **قبل قبول دفع ذاتي (self-serve)** | دمج Paddle/Lemon Squeezy لخطتي التجربة والمؤسسي فقط |
| **متى ما طُلِبت تعاقدياً** | DPA + بند القانون الحاكم + سياسة استرجاع مكتوبة رسمياً (لا افتراضية) |
| **عند نمو حقيقي في عدد العملاء المدفوعين** | تقييم إضافة بوابة خليجية محلية بناءً على طلب فعلي، لا استباقاً |
