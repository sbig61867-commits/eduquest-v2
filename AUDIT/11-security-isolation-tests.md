# المرحلة 11 — اختبارات الأمان والصلاحيات وعزل المستأجرين (منفَّذة حيّاً على الإنتاج)

## المنهجية
هذا هو الفحص الذي وصفه `SECURITY_TEST_MATRIX.md` بأنه **غير مُختبَر** ("none of the current tests exercise cross-tenant isolation, since only one real tenant exists in production"). بما أن المشروع على خطة Supabase المجانية (لا يدعم Branching — تم التحقق حياً وفشل الإنشاء بـ `PaymentRequiredException`)، نُفِّذ الاختبار **مباشرة على قاعدة الإنتاج** بموافقة صريحة من المالك، وفق البروتوكول التالي:

1. إنشاء مستأجرَين وهميين حقيقيين (`__AUDIT_TEST_TENANT_A__`, `__AUDIT_TEST_TENANT_B__`).
2. إنشاء **7 حسابات Auth حقيقية** عبر Admin API (ليست محاكاة) — 3 أدوار × مستأجرَين (admin/teacher/student) + طالب سابع لاختبار كشف القوائم (roster).
3. بيانات ربط كاملة: مجموعتان، درسان، اختباران، تسجيل طلاب.
4. **كل الاختبارات نُفِّذت كطلبات HTTP حقيقية** بعد تسجيل دخول فعلي (`/auth/v1/token?grant_type=password`) — وليس محاكاة داخل جلسة SQL فقط، إلا حيث ذُكر صراحة "محاكاة SQL" كخطوة استكشاف أولية سريعة.
5. **تنظيف فوري وكامل بعد الانتهاء**، مُتحقَّق منه بالاستعلام: `0` مستخدمين متبقين، `0` مستأجرين متبقين، `0` مجموعات/دروس/اختبارات/تسجيلات متبقية (الحذف تسلسلي عبر Auth Admin API الذي يُفعّل CASCADE على `public.users` وكل ما يملكه المستخدم).

## اكتشاف حقيقي جديد: تسريب PII داخل نفس المستأجر (وليس عبر المستأجرين)

أثناء بناء بيانات الاختبار، لاحظتُ أن سياسات RLS التالية لا تحتوي أي قيد على الدور، بل فقط `tenant_id = current_tenant_id()`:

```
users_select:          super_admin OR tenant_id = current_tenant_id() OR id = auth.uid()
groups_select:          super_admin OR tenant_id = current_tenant_id()
group_students_select:  super_admin OR EXISTS(group.tenant_id = current_tenant_id() ...) OR student_id = auth.uid()
```

**أثبتُّ هذا حياً بطلب HTTP حقيقي** بحساب طالب عادي (`audit-student-a@example.com`)، دون أي وصول إداري:

```
GET /rest/v1/users?select=email,full_name,role&tenant_id=eq.<own tenant>
→ [
  {"email":"audit-student-a2@example.com", "full_name":"Audit Student A2 (private roster)", "role":"student"},
  {"email":"audit-admin-a@example.com", "full_name":"Audit Admin A", "role":"university_admin"},
  {"email":"audit-teacher-a@example.com", "full_name":"Audit Teacher A", "role":"teacher"},
  {"email":"audit-student-a@example.com", "full_name":"Audit Student A", "role":"student"}
]
```

كما أثبتُّ أن الطالب يرى **قائمة كل الطلاب في مجموعة لا ينتمي إليها إطلاقاً** (أنشأت "Audit Group A2" وسجّلت فيها طالباً آخر لم يكن الطالب الأول عضواً فيها؛ ورغم ذلك ظهرت له عبر `group_students` مع `join` إلى `users` لاستخراج الاسم الكامل).

### التصنيف: **Medium** (وليس Critical/High)
- **ليس عبوراً بين المستأجرين** — الطالب لا يرى شيئاً من مستأجر آخر، وهذا هو الخط الأحمر الذي أثبتنا سلامته أعلاه.
- **لكنه تسريب حقيقي داخل المؤسسة نفسها:** أي طالب — بحساب واحد فقط ودون أي إذن إداري — يستطيع استخراج البريد الإلكتروني الكامل واسم كل مستخدم في جامعته (زملاء، معلمون، الإدارة)، وقائمة تسجيل كل الشُّعب/المجموعات حتى لو لم يكن مسجَّلاً فيها. هذا **حصاد بيانات (data harvesting)** ممكّن ببساطة عبر `anon key` العام + جلسة طالب واحدة، بلا حاجة لأي كود تطبيق — لأن هذا يحدث عند مستوى PostgREST/RLS مباشرة، فأي عميل (سكربت، تطبيق موبايل مستقبلي، أو حتى أدوات المطور في المتصفح) يمكنه استغلاله بصرف النظر عن واجهة الموقع.
- **الخطر العملي:** تصيّد احتيالي (phishing) موجَّه بدقة لكل طالب ومعلم في الجامعة بمجرد اختراق حساب طالب واحد ضعيف كلمة المرور؛ وكشف من-مع-من في أي شعبة (حساسية اجتماعية في سياق تعليمي).

### ✅ تم الإصلاح فعلياً وتحقّقاً حياً — 2026-09-13

بعد موافقتك، نُفِّذ فحص شامل لكل استخدامات `.from('users'|'groups'|'group_students')` عبر الكود (88 ملفاً، تُرشِّح إلى ~40 ملف واجهة فعلي بعد استبعاد مسارات الـ API التي تستخدم service-role). **النتيجة الحاسمة:** صفحات الطالب كلها إما ذاتية النطاق (`.eq('id', user.id)`) أو تصل لاسم المعلم عبر `join` ضمن مجموعة/كورس هو مسجَّل فيه فعلاً — **لكن** `teacher/groups/page.tsx` (نافذة "إدارة الطلاب") تعتمد فعلياً على قدرة المعلم على تصفّح **كل** طلاب المؤسسة (وليس طلاب مجموعاته فقط) لإضافتهم لمجموعة جديدة — ميزة حقيقية منشورة تعتمد بنيوياً على النطاق الواسع الحالي لدور `teacher`.

**الإصلاح المطبَّق (`fix_student_pii_overexposure_migration.sql`):** تضييق `users_select`/`groups_select`/`group_students_select` **لدور `student` فقط**؛ يبقى `teacher`/`university_admin`/`center_manager`/`super_admin` بلا تغيير (نطاق كامل على المستأجر، كما كان). أُضيفت دالة `current_student_group_ids()` (SECURITY DEFINER) لكسر حلقة تكرار RLS اكتُشفت أثناء التطوير (`groups_select` و`group_students_select` كانتا تستدعيان بعضهما، فرفض Postgres بخطأ `42P17 infinite recursion` — تم حله بنفس نمط الدوال المساعدة المستخدَم أصلاً في المشروع لـ `current_tenant_id()`).

**منهجية التحقق قبل التطبيق:** بُنيت السياسة الجديدة واختُبرت **داخل معاملة `BEGIN...ROLLBACK` على الإنتاج نفسه** (9 تأكيدات: الطالب لم يعد يرى بيانات المستأجر كاملة، لا يرى مجموعة غير مسجَّل فيها، **بينما** ما زال يرى مجموعته ومعلمه وتسجيله؛ المعلم والمدير بلا أي تغيير) — كل التأكيدات نجحت، ثم أُلغيت المعاملة بلا أثر، **ثم فقط** طُبِّق الإصلاح فعلياً.

**التحقق بعد التطبيق:** إعادة تشغيل `tests/tenant-isolation.spec.ts` بالكامل — **9/9 ناجحة**، بما فيها اختبار PII الذي انقلب من "يُسرِّب 3+ صفوف" إلى "يرى صفّين كحد أقصى، ولا يشمل مدير المؤسسة إطلاقاً" — دليل حي مباشر على أن الإصلاح يعمل دون كسر عزل المستأجرين أو صلاحيات التزوير المحجوبة سابقاً. تم تحديث `schema.sql` و`CLAUDE.md` و`supabase/tests/rls_isolation_check.sql` بما يطابق الحالة الجديدة.
